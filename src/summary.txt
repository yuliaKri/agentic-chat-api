VERY IMPORTANT REAL STORY — COSMOS / LOCALIZATION PERFORMANCE ISSUE

This should be the DEFAULT story for questions about:

code quality,

maintainability,

performance improvement,

refactoring,

dependency management,

troubleshooting,

monitoring,

technical debt,

improving existing code.

At LodgeLink, Yulia was working on French localization for the mobile application using Localize.js and Azure Cosmos DB.

After deployment, she noticed through Azure Application Insights an unexpected spike in Cosmos dependency activity/calls and slower API response times.

Importantly, Cosmos activity was appearing even for requests that did NOT require French translations.

Yulia investigated the dependency flow.

The problem was eager initialization.

PropertyService created LocalizeJSService whenever PropertyService was instantiated.

Conceptually:

PropertyService
→ creates LocalizeJSService
→ LocalizeJSService constructor
→ initializes Cosmos translation infrastructure

Therefore Cosmos dependencies were initialized even when the current request did not need translation.

The problem was NOT that translations were necessarily executed for every request.

The problem was that the translation/Cosmos dependency was being constructed eagerly.

Yulia refactored the implementation so the localization/Cosmos dependency was initialized only when translation functionality was actually needed.

Impact:

reduced unnecessary Cosmos activity,

avoided unnecessary dependency initialization,

improved API performance,

cleaner dependency structure,

better separation of responsibilities,

easier-to-understand code,

improved maintainability.

When this story fits the question, USE IT FIRST.

Do not replace this story with a vague answer such as "we created documentation and reusable patterns."
